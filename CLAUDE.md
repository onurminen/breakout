# breakout

Course project for CS-E4780 Scalable Systems and Data Management (Aalto, 2026): a Go streaming pipeline over the DEBS 2022 tick data that computes EMA38/EMA100 per symbol over 5-minute windows (Query 1) and buy/sell advisories on crossovers (Query 2). Deadline 27.11.2026, together with a 4–5 page ACM-style report (`report/`, Typst).

Start with `README.md` (status, commands), then `docs/architecture.md` and `docs/windowing.md`. Remaining work is tracked as GitHub issues.

## Working principles

- **Simplest solution first.** Build the smallest version that does the job, then improve it if measurements or the assignment demand it. Earlier decisions are not binding when they turn out over-engineered: a simpler approach is welcome, but say why it is enough, and update `docs/decisions.md` and the affected docs.
- **No unrequested features.** No options, flags, abstractions or "for later" code that the task does not need. A small focused change is easier for the group to review and understand.
- **Every group member must be able to explain the code.** The report and its contributions section depend on it. Prefer plain, obvious code over clever code, and explain concepts when asked.
- **Few dependencies.** Standard library first; the chosen libraries are listed in `docs/architecture.md` (section "Technology").

## Code style

- Readable, descriptive names (`eventTimeMs`, `closesAt`, `position`); short names only for receivers and tiny scopes.
- Units in names where they matter: `…Ms` for epoch milliseconds, `…Ns` for wall-clock nanoseconds.
- **Comments only where the code cannot speak for itself:** a non-obvious why, a unit, a trap (e.g. the integer overflow note in `tools/enginecheck`). No comments that restate the code; a comment that makes a function harder to read is worse than none. Doc comments on exported names, one or two lines.
- Tests next to the code, table-driven where there are many cases. Tests that need the real CSV files or a running service skip themselves when the input is missing (see `DATABASE_URL` in `internal/store`).
- `gen/go/` is generated by `buf generate` and committed; never edit it by hand.

## Documentation

- Docs describe the system as it is, not how it got there. Only the most relevant aspects of the implementation: no minor details, debugging stories or hiccups.
- Short, pleasant to read, no filler. Impersonal or passive voice ("the engine closes…", not "we close…").
- Say "assignment" or "assignment description", not "spec".
- One home per topic: the why goes into `docs/decisions.md`, the how into the other docs; link instead of repeating.
- A claim about the data needs a check in `tools/datacheck/` behind it. Do not document assumptions verified only by a throwaway script.
- Update `README.md`'s status table and the affected docs in the same change as the code.

## Git

- Agents show the commit message for approval before committing and never push unless asked.

## Fixed by the assignment

These follow the assignment description and should not change:

- Price = `Last`.
- Tumbling 5-minute windows starting at 00:00; a window's price is the event with the highest event time in it.
- `EMA_j = price · 2/(1+j) + previous · (1 − 2/(1+j))`, starting from 0, for j = 38 and 100.
- Buy when EMA38 crosses above EMA100, sell when it crosses below, with the strict and non-strict comparisons from the assignment.
- All symbols are computed; updates are sent only for the symbols a client subscribes to.

## Decisions made so far

Reasons are in `docs/decisions.md`. Data-backed facts come from `tools/datacheck` (`docs/data.md`).

**Data and windowing**

- Event time = `Date` + `Trading time` (epoch ms, treated as UTC). The assignment names `Trading date`, but it is empty for about 92% of price events.
- Files are replayed in date order and, within a file, in file order. Each symbol's events are already in event-time order, except Wednesday's 5,506 index events at 01:00, which arrive about 18 hours late and are dropped as late.
- About 79% of lines are not price events; lines with `Last` ≤ 0 or unparsable fields are dropped and counted per reason.
- Windows close on watermarks (highest event time sent, every 1 s of event time, to every partition, finally `MaxInt64`) plus a 1 s grace period.
- Empty windows are skipped: no result, EMAs unchanged. About 73% of windows are empty.
- EMA state carries across days. A symbol's first window always produces a buy, sent with `warmup = true`.
- Expected whole-week totals, from `go run ./tools/enginecheck data/*.csv`: 1,855,645 results, 5,506 late events. Any change to the engine or to ingestion must keep them.

**System**

- One Go module, one binary per service in `cmd/`, shared code in `internal/`. Kafka between services, Protobuf messages, Postgres for history, Prometheus/Grafana/cAdvisor for metrics, everything on one machine with Docker Compose.
- Each `ticks` partition is owned by one goroutine with its own `engine.Engine`, so the engine needs no locks.
- Kafka has no volumes: `docker compose down` deletes all topics' data, which experiments rely on for a clean start.
- Latency is measured on the shared wall clock and ends when a result is published to Kafka, not in the browser.
- Parsing dominates CPU: one core parses about 870k events/s, so the whole week through the engine core takes about 70 s.

**Not set in stone.** These were reasonable defaults, and can be simplified when they get in the way: 12 partitions for `ticks` (another fixed number works, even 1 for a first version), one partition for the result topics, a separate sink service, the engine re-reading partitions instead of committing offsets, the API proxying KPIs from Prometheus, metric names, `kafka-exporter`, the chart library, and the experiment list in `docs/evaluation.md`. Changing one means updating `docs/decisions.md` and the affected docs.
